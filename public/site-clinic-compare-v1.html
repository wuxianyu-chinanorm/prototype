LibreClinica

开源 EDC。完整继承 OpenClinica 3 的合规架构；社区公开测试规范，降低 GCP / 21 CFR Part 11 自验证成本。
开源自部署eCRF / Query / Audit

用户 root　　密码 12345678
探活 200 · 未登录会跳到 pages/login/login

解决什么问题

解决的是临床试验电子数据采集与核查：按方案建库，现场只填当前访视表单，监查发质疑，改数必须写原因，签完锁定再导出。不解决导检、称重、仪器。

技术架构

形态
Java WAR · 浏览器
谱系
OpenClinica 3.x 社区分叉
数据
研究 / 受试者 / 事件 / CRF 条目 + 审计追踪
验证资产
公开 Test Specifications + 社区测试结果

操作流程

  1. 登录用 root 进主菜单。首次可能要选中心 / 角色。
  2. 建研究Study → 访视事件 → CRF 表单（或导入 ODM）。
  3. 入组受试者Subject → 分配到当前研究。
  4. 按访视录入只打开当天事件的 CRF；逻辑核查自动拦错或发 Query。
  5. 质疑闭环监查发问 → 现场回复 → 关闭。改值必填原因。
  6. 签名与锁库研究者电子签 → 数据管理冻结/锁定 → 导出。
对 KIS不能当现场系统。应照抄：审计追踪、Query 生命周期、改数原因、电子签名、冻结锁定、以及「公开测试规范」这种可审计的自验证包。eCRF 可做附属采集层，不要替换访视操作台。

Mautic

开源营销自动化，对标商业营销云。行业是获客漏斗，不是临床招募软件；但「线索从哪条广告来、多久没人联系」这条链路是现成的。
开源自部署广告归因 / 培育

解决什么问题

把广告 → 表单 → 线索 → 培育 → 回访留在自己服务器上。专业医疗招募软件通常不管 UTM 和线索老化；Mautic 管的就是这个。

形态
PHP · Symfony · MySQL
核心对象
Contact / Campaign / Form / Email / Segment
追踪
落地页像素、UTM、渠道、打开与点击

画布：条件分支、等待、发信、改阶段

操作流程

  1. 登录看板看新增线索、活动、待办。
  2. 建渠道与表单Channels / Forms：落地页或嵌入表，带 UTM。
  3. 线索入库提交后成为 Contact，记下源广告与首次触达时间。
  4. 分段Segments：按来源、城市、是否已预约切群。
  5. 画 Campaign例如 24 小时未联系 → 提醒销售；3 天未预约 → 补一封。
  6. 回访闭环人工改阶段（已约 / 已筛 / 失败），后续动作停掉。
对 KIS不要用它管入组后的访视。建议参考或旁路接入：线索来源字段、无人跟进计时、培育画布。招募台补「来源 + 上次联系时间」，比自研整套营销云便宜。

解决什么问题

让小诊所把当天来的人、叫到哪、病历在哪、复诊提醒数字化。场景是门诊，不是按方案执行的访视日。

操作流程

  1. 打开首页先看当日队列/工作台入口。
  2. 登记 walk-in无预约上门：建档或检索老患者。
  3. 候诊与叫号按到达顺序或诊室叫下一位。
  4. 看诊写病历进入患者 vault 记主诉/处方（以实际菜单为准）。

解决什么问题

给研发一条合规向的医疗数据 API：身份、就诊、问卷、文件都按 FHIR 资源存，而不是自创表结构。适合做互操作和审计模型，不适合直接给现场老师点「称重」。

操作流程

  1. 登录项目进入 Project 控制台。
  2. 建 Patient标准资源，不要一上来自定义大表。
  3. Encounter一次到访对应一次 Encounter。
  4. Questionnaire / Response用问卷资源采集，而不是随意 JSON。
  5. 看 Audit / Access谁读过谁写过，按策略收紧。
对 KIS不要把现场流程迁到 Medplum。可参考：到访=Encounter、量表=Questionnaire、附件=DocumentReference。互操作或对外 API 时再认真评估 FHIR，不作为 2026 现场主干。

医院级开源 EMR 里的「服务队列」：分诊、等候、叫号。官方 Demo 功能全，控制台报错是共享脏库和 CSP，不是你的浏览器坏了。

解决什么问题

门诊人在哪一站、下一个该谁。和功效评价的导检相似的是「空间+队列」，不同的是它按医院服务台，不按方案访视块。

操作流程

  1. 登录admin / Admin123，选 Location，否则进不去业务页。
  2. 打开 Service Queues看各队列等候人数。
  3. 入队患者挂到某个服务队列（分诊/抽血/诊室）。
  4. 叫号 / 改状态waiting → called → served，或转队列。
  5. 结束完成或失约，队列长度变化。
对 KIS导检状态机最值得看：站点、队列、叫号、转诊。不要引入 OpenMRS 的整套概念（Visit Type、Location 树）。KIS 对应的是访视日路线上的工位，不是医院科室。
