① 市面上这些系统没有一套能直接当我们的业务系统用——它们解决的是"药物临床试验的表单数据采集与核查"， 而我们化妆品人体功效评价的工作量有七成落在现场运营（导检排班、测试品发放/回收/称重、仪器数据落盘、图像管理、日记卡齐套、归档清单）上，这部分通用 EDC 完全不覆盖。

OC

OpenClinica 3.x 社区版

LGPL 开源自行部署官方不提供支持/验证
世界第一个"商业开源"临床试验软件。美国波士顿 OpenClinica LLC 主导，2005 年起持续发布。
行业地位
开源 EDC 的鼻祖与事实参照物。全球最大的开源 eClinical 用户群之一，学术中心、注册登记研究（Registry）、中小申办方长期使用；几乎所有后来者（含 LibreClinica）都是它的分支或对标对象。
主要服务行业
药物/器械临床试验、研究者发起研究（IIT）、疾病注册登记库、公共卫生项目。以"受试者-访视-表单"三层结构为核心，天生面向多中心 GCP 场景。
凭什么是权威
① 它把 GCP / 21 CFR Part 11 的要求逐条翻译成了软件功能（审计追踪、电子签名、角色权限、质疑管理），是"合规如何落到界面上"的教科书；② 原生基于 CDISC ODM 标准建模，数据结构本身就是行业标准；③ 十余年被真实核查检验过。
当前状态（已核实）
社区版最新 3.17.3，2025-11-12 发布；GitHub 主仓 ~500 星、100+ 开放 issue。官网明确："我们无法为免费社区版提供任何支持或服务，下载、实施、集成与验证由使用者自行负责"。

技术栈

Java（Spring MVC）PostgreSQLApache Tomcat FreeMarker / JSP 模板XSLT（数据抽取）PL/pgSQL SOAP Web Services（可选 WS 包）RESTful API（3.x 后期）CDISC ODM 1.3 XML

技术判断：典型 2010 年代 Java 企业架构，前端是服务端渲染的老式页面。我方技术栈为 Python/Django， 若自部署将形成第二套异构技术栈（JVM + Tomcat 运维、Java 人力），这是隐性成本的最大来源。

真实工作流（这是最值得我们抄的部分）

  1. 建库：定义研究与站点创建 Study → 下挂 Site（多中心）→ 定义研究事件 Event Definition（≈ 我方的 T0/T1W/T4W/T8W 访视）。
  2. 设计 eCRF用 Excel CRF 模板（Sections / Groups / Items / ResponseSets 多个 sheet）离线写好后上传，系统解析生成表单。表单有版本号，版本可 Available / Frozen / Locked。
  3. 写逻辑核查 Rules以 XML 规则文件上传：目标项 + 表达式 + 动作（弹提示 / 自动发质疑 / 置值 / 发邮件）。支持跨表单、跨访视引用。
  4. 分配权限角色：Data Manager / Study Director / Investigator / Clinical Research Coordinator / Monitor / Data Entry Person，权限按 Study-Site 层级授予。
  5. 入组受试者登记 Study Subject ID、二级 ID、入组日期、性别/生日 → 按事件定义排访视日程。
  6. 数据录入Initial Data Entry → （可选）Double Data Entry 双人双录比对 → Complete。录入中实时触发核查。
  7. 质疑管理（Discrepancy Notes）四种类型：Failed Validation Check / Query / Reason for Change / Annotation；状态流转 New → Updated → Resolution Proposed → Closed，全程留痕、可分配给具体人、可导出质疑清单。
  8. 源数据核查 SDV监查员逐项/逐表勾选"已与原始记录核对"，形成 SDV 覆盖率报表（这就是风险化监查的基础）。
  9. 电子签名研究者对受试者/访视级数据签名，签名绑定用户名+密码+时间戳+含义声明，符合 Part 11 的"签名不可与记录分离"。
  10. 冻结与锁定Event/CRF 级 Freeze → Lock；锁定后任何修改必须留 Reason for Change，审计追踪不可删除。
  11. 数据抽取导出 CDISC ODM 1.3 XML（含 OpenClinica 扩展）、制表符文本、SPSS 等格式，抽取任务可定时。

我方可直接拿走的设计

  • "表单版本 + 数据版本"双轨：方案修订（我方有 V1.0→V3.0 方案 + 方案修订记录表）时，老数据仍绑定老版本表单，不被改写——这正是我方"方案偏离/修订"最容易出错的地方。
  • 质疑四分类：把"系统核查失败"和"人工提问"和"修改原因"分开建模，比我方质量管理台目前笼统的"问题项"更清晰。
  • SDV 勾选粒度：可精确到字段级，支撑"关键数据 100% 核查、非关键抽查 20%"的分层策略。

LibreClinica

LGPL-3.0 完全开源自行部署零授权费提供自验证测试规范
OpenClinica 3.14 的社区正统分支（2019 年 fork），由德国 ReliaTec GmbH 牵头，德国癌症研究中心（DKFZ）、亚琛工业大学医院（RWTH Aachen）等机构参与维护。
行业地位
开源 EDC 的当前最优自部署选项。规模不大（GitHub ~60 星、30 位贡献者）但极其专注：由真实在用的欧洲学术医疗机构自用驱动开发，属于"小而真"的项目，而非营销驱动。
主要服务行业
欧洲大学医院、癌症研究中心、研究者发起试验与注册登记研究。典型用户画像：有 IT 部门、预算有限、且必须把数据留在自己机房（德国数据保护要求极严）——与我方处境高度相似。
凭什么是权威
① 完整继承 OpenClinica 的合规功能架构；② 官方公开"测试规范（Test Specifications）"供用户做自我验证，并发布社区测试结果——这是开源项目里极罕见的做法，直接降低了 GCP / 21 CFR Part 11 环境下的验证成本；③ 修掉了 3.x 大量遗留 Bug、升级了依赖库，安全性优于官方遗留仓库。
当前状态（已核实）
最新稳定版 1.4.0，2025-07-10 发布；代码仓库 2026-05 仍有提交，项目活跃但节奏慢（约每年一个稳定版）。官方提供从既有 OpenClinica 实例的迁移说明，并列出可付费支持的专业合作伙伴名单。

技术栈（官方明确的版本矩阵，可直接交运维）

工作流

与 OpenClinica 3.x 完全一致（见上文 11 步），差别在稳定性与细节修复，不在流程。官方文档按角色分册：给研究者/录入员一本、给监查员一本—— 这种"按角色写手册"的做法，建议我方 KIS 3.0 的培训材料直接照搬（对应我方"项目培训记录表"环节）。

我方可直接拿走的设计

7给领导的三条路线

路线 A · 建议

KIS 为主干，照抄 EDC 内核

现场流程继续在 KIS。单独做薄的数据管理内核：数据字典、表单版本、逻辑核查、质疑、审计追踪、电子签名、冻结锁定、标准导出。

为什么是权威做法：机制来自 OpenClinica / LibreClinica / Viedoc / Rave，不自创名词。

  • 数据留在 253/188/118
  • 和导检、称重、仪器是同一个研究 ID
  • 不按项目给境外厂商交月租
  • 验证文档要自己写，LibreClinica 的测试规范可当提纲
  • 表单体验要对准 Castor / REDCap，否则现场不用
软件授权：0。成本在研发与验证人月。对照锚点：OC4 公开价约 $3,000–3,750/月/项目，项目一多，自研更容易算得过账。
路线 B · 备选

LibreClinica 只做采集，KIS 做现场

253 上部署 LibreClinica 1.4，eCRF 与质疑放那里，KIS 用受试者编号和访视编号对接，不双向乱写。

  • LGPL，可商用自部署
  • 审计追踪和角色是现成的
  • 有自验证测试规范
  • Java + Tomcat，和第二套栈长期共存
  • 界面老、中文弱、没有日记卡和称重
  • 社区小，故障主要靠自己
授权：0。隐性成本：JVM 运维、验证、双系统对账。适合"先有一个能被核查的库"，不适合当最终形态。

8必须照抄的六项机制（不要自创）

这些不是功能清单，是监管和客户审计时会逐条问的东西。OpenClinica、LibreClinica、Viedoc、Rave 的实现细节不同，名词和状态机应当一致。

#机制权威来源怎么做我方落地要求
1审计追踪谁、何时、旧值、新值、原因、操作含义。记录不可删改，管理员也不能关。访视数据、知情、称重、样品、权限变更全部进同一条审计，能按受试者导出。
2质疑生命周期系统核查失败、人工提问、修改原因、批注分开。状态：新建 → 更新 → 提议解决 → 关闭，可指定回复人。质量管理台不要只用"问题项"。自动质疑和人工质疑分类型。
3源数据核查 SDV字段级勾选"已与原始记录核对"。Rave 进一步做成靶向：关键字段 100%，其余按比例。先定义我方关键数据（主要终点仪器值、不良事件、知情签署），再定核查比例。
4电子签名签名绑用户、时间、含义（"我确认数据准确"），签完记录锁定，不能把签名和记录拆开。研究者签临床评估，数据管理员签锁库。账号密码或同等认证，不接受只点一个按钮。
5冻结 / 锁定 + 修改原因冻结后默认不能改；要改必须填原因，写进审计。方案改版后，旧数据仍绑旧表单版本。对应我方方案 V1→V3。生产变更走草稿审批，对齐 REDCap 的 Draft 模式。
6数据字典 + 标准导出REDCap 用一张表定义全部字段；OpenClinica 导出 ODM XML。Pinnacle 21 证明"校验报告要带规则编号"。我方字段设计 HTML 升级成可导入字典。导出包含数据、字典、审计、质疑清单。

工作流上再抄三条，避免以后返工

  • 访视 × 表单矩阵（REDCap）：一张网格定义 T0 / T1W / T4W / T8W 各填什么，替代口头主测试计划。
  • 设计修订不停机（Viedoc）：方案偏离或修订时，现场访视不中断，新版本只作用于未填表单。
  • 研究主数据一棵树（Veeva）：合同、伦理批件、方案、知情、访视、样品、报告共用一个项目编号。目录 01–19 是这棵树的纸质版。

9四周落地，不先花钱

  1. 第 1 周 · 观摩申请 Viedoc 测试环境（建库不需要合约）。注册 Castor 账号只搭一张表。REDCap 只用官方 Demo 看数据字典，不申请许可。Pinnacle 21 Community 4.2.0 装到统计岗电脑，避开 snapshot 预发布版。
  2. 第 2 周 · 开源对照在 253 用 Docker 起 LibreClinica 1.4（OpenJDK 11、Tomcat 9、PostgreSQL 13/14）。不接入生产数据。同步把 OpenClinica 3.17 社区版只做对比，不作为推荐运行版。
  3. 第 3 周 · 用 C25005046 跑通只迁 4 张表：受试者信息、一次访视的临床评估、一次仪器测量、一条不良事件。走完录入、自动质疑、人工质疑、修改原因、签名、锁定、导出。称重和导检故意不迁，用来演示 EDC 的边界。
  4. 第 4 周 · 决策页产出一页：KIS 缺口清单（对照第 8 节六项）、LibreClinica 双栈成本、Viedoc 与太美询价回函。领导只批路线 A / B / C，不在本阶段签采购。

询价函里就这 8 问（三家用同一份）

  1. 按机构包年、不限研究数的价格，和按研究计费的价格各是多少？
  2. 用户数是否另收费？研究者、CRC、监查、品牌方只读账号是否同价？
  3. 数据能否放在中国境内我方或厂商机房？个人信息是否出境？
  4. 我方人员能否自己改 eCRF？改版是否停机？旧数据是否绑定旧版本？
  5. 审计追踪、电子签名、质疑、SDV、锁定是否在基础包内？验证文档是否交付？
  6. 日记卡 / ePRO 是否另计费？
  7. 是否提供 API，以便 KIS 写入仪器结果、称重和签到状态？
  8. 合同结束后数据导出格式是什么？导出是否包含审计和质疑？保存多久、费用多少？
四周结束时的验收业务负责人能在沙盒里指出：哪一步比纸质 CRF 好，哪一步现场仍然必须用 KIS。没有这份对照，不进入采购评审。
