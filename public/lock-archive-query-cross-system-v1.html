0结论先行

① 锁库不是关库。它是一次有法律意义的声明：某一粒度上的数据从此成为统计分析与申报的官方版本。业内把它拆成冻结（Freeze）与锁定（Lock），再拆成表单 / 受试者 / 中心 / 数据库四级，几乎所有成熟 EDC 都走这一套，而不是给整台数据库加只读。
② 归档不是把数据搬走。试验主文件（TMF/eTMF）、数据库快照（带哈希的导出批次）、以及实验室/病历系统的病案封存，是三条不同的归档。混用「归档」一词会让前台签出、工单关闭和检查员要的证据包互相打架。
③ Query 不是校验规则，也不是一张工单模板那么简单。它是挂在「某个数据节点」上的受控对话，有状态机、角色、与改数/签名/锁库的门禁耦合。技术上：附着方式像切面，本体必须是一等公民聚合根——只做 AOP 拦截或通用 Ticket 而不建模「指向哪一条值、哪一次质疑线程」，过不了核查。

0b人话版：假设你完全没做过药物试验

先忘掉英文缩写。把功效评价想成：诊所每天给受试者测数据，最后要出一份报告交给客户或检查。下面所有词，都是为了保证「报告里的数字」经得起追问。

先用一个完整小故事串起来

有一个祛斑项目，100 个人测完了。统计同事准备算平均值。这时现场突然发现：第 37 号受试者某天的「色斑面积」填成了 999，明显像手滑。如果统计已经开始算了，你又把 999 改成 9.9，报告就会对不上「我当初拿去算的那一版」。所以行业规定了三步：

  1. 有人必须正式问一句：「999 是不是填错了？」现场书面答：「是，已改成 9.9。」这句问答要留着。——这叫质疑（Query）。
  2. 所有这种问完了、该改的改完了，负责人点一次：从现在起，用来出报告的数据不许再改。——这叫锁库。
  3. 把「锁住的那一版数据 + 谁改过什么 + 那些问答」打包存好，三年后检查员来还能打开。——这叫归档。

如果你只在系统里点一个「项目已结束」，检查员问「当时拿去统计分析的是哪一版？999 是谁改的？」你答不上来。所以不能用一个「已闭环」按钮代替这三件事。

六个卡片，用现场的话说

词你可以把它想成不是什么
逻辑核查 Edit check 表单上的自动校验：年龄填了 3 岁、血压填了 300，保存时弹窗「这不合理」。像网银转账时「金额不能为负」。 不是质疑。它只是规则。规则响了，系统可以顺便开一张质疑单让人解释，那张单才是 Query。
质疑 Query 贴在某一个格子上的「官方便利贴 + 来回留言」。例如贴在「色斑面积=999」上：监查问、CRC 答、数据管理员点关闭。必须能说出：问的是哪个人、哪一天、哪一个字段。 不是前台工单（导检、称重、叫号）。工单是「去干活」；质疑是「这个数字对不对」。也不是随便在聊天软件里问一句——口头问完没有记录，检查时等于没问过。
电子签名 Sign 医生/研究者点一下：「这张表我看过，我对内容负责」。像在纸质病历上签字。常常先签完，再允许锁。 不等于锁库。签了只表示有人负责，数据还可以按流程再改；锁了才是「统计用这一版」。
冻结 Freeze 对现场说：「你们先别改了，让数据管理员把尾巴收干净。」像商店打烊前「停止点单，厨房还在出最后几份」。 还不是最终锁死。Rave 这类系统特意分成两步，避免太早锁死又要大批解锁。
锁库 Lock 对所有人说：「这一版就是出报告用的官方数据。再改等于改历史。」像上市公司财报报出后不能偷偷改账，要改必须走重大流程并留痕。 不是把服务器关机，也不是 DBA 把整库设只读。通常是：这个项目（或某张表、某个人）在业务系统里不能再保存。别的项目照常做。
归档 Archive 把「锁住的那一版 + 改数记录 + 质疑对话 + 方案知情等文件」当成一个证据包存起来，写清哈希（防调包）、存到哪年。三年后打开应仍是当时那包，不是「现在库里长什么样」。 不是电脑备份（备份会被新备份覆盖）。不是受试者签出。不是把工单点关闭。签出只表示人走了，数据还可能改、也还没打成证据包。

表格里另外几个词（同样用人话）

词人话和锁库/质疑的关系
SDV 源数据核查 监查拿着系统里填的数，去对原始东西：知情同意纸、仪器打印条、护士记录。看「系统里的 9.9」是不是仪器当时打出来的。 对不上就会开质疑。SDV 做完的比例，常常作为「能不能锁库」的检查项之一。但 SDV 本身不是锁。
偏差 Deviation 过程没按方案走：该第 7 天来却第 10 天才来、该用 A 仪器用了 B。这是「事没做对」，不是「格子里数字填错了」。 可以和质疑互相链接。很多 SOP 规定：未关闭的偏差也不能锁库。但它不是贴在某个字段上的问答。
CAPA 出了偏差之后：纠正（这次怎么补）、预防（下次怎么避免）。像质量体系里的「整改报告」。 常跟偏差绑在一起，作为锁库前「质量事故是否收口」的检查。
工单 咱们诊所自己的待办：带去称重、去拍 Visia、去发测试品。 看起来也像一张「待处理单」，但检查员不认它当质疑，除非它明确指向某一个数据格子，并且关掉它会进入锁库检查。
CRF / eCRF 病例报告表。纸质叫 CRF，电脑里填的叫 eCRF。就是「这一访要填哪些格子」。 质疑通常贴在 eCRF 的某个格子上。
DM 数据管理员（Data Manager）。专职盯数据清不清、质疑关没关、能不能锁。 冻结之后现场不能改，往往还允许 DM 处理质疑。
Rave Medidata 公司做的一套商业 EDC，药厂试验里特别常见。不是开源，也不是医院系统。 报告拿它当「行业老师傅」：冻结和锁定分两步，就是它这一路产品做出来的习惯。

为什么一定要分成三件事（再讲一遍，不绕）

三个不同的人会问三种不同的话：

  • 做统计的人：「我算的 Excel / 数据集，会不会明天又被现场改掉？」→ 需要锁库，锁的那一刻有编号、有时间。
  • 来检查的人：「三年后你给我看：当时那份数据、改数记录、知情同意、仪器原始图，还在不在？有没有被调包？」→ 需要归档包，不是「现在登录系统随便点点」。
  • 盯质量的人：「这个 999 当时有没有人问过？谁答的？答完你为什么还留着/为什么改掉？」→ 需要质疑线程，不能靠记忆。

顺序通常是：先把质疑问完（数据清洁）→ 再锁 → 再把锁住的那一版打成包归档。中间可以有「冻结」当缓冲：现场先停手，DM 收尾。

和咱们诊所日常最容易混的一句 受试者签出、测试品回收完、工单关掉，只说明当天现场活干完了。数据还可以改、质疑还可以开、报告还没钉死。所以前台不能对 QA 说「人都走了等于已经归档」。
读完这一节再读后面 后面章节会写各软件怎么做、Query 算不算技术切面。那些是给已经听懂「三件事」的人看的。你只要记住：质疑是问某个数字，锁库是钉死出报告的那一版，归档是把那一版连同证据封存。 下一节把「开项目 → 收数 → 关项目」画成时间轴，并写清每个角色站在哪、Query/锁/归档技术上建议怎么做。

0c一个项目从开到关：节点、角色、技术怎么做

把一个功效评价项目当成一条时间线。下面不绕术语：先认人，再走路，再标「Query 能出现在哪、锁必须在什么之后、归档必须在什么之后」，最后给纯技术推荐。

先把你列的词对成「一种动作」

词一句话发生在时间线上的哪里
逻辑核查就是保存时的校验（年龄<0 不让存，或存了立刻告警）只要还在填数，每次保存都可能跑。锁库之后现场保存直接失败，校验也跑不到。
Query 质疑针对某一个已保存的数字的正式问答单从第一条数据进库就可以开，直到硬锁成功。锁后原则上不能再开；除非解锁。
偏差针对过程没按方案走（来晚了、用错仪器），不是改格子从入组/访视开始随时记。硬锁前应关闭或豁免。和 Query 可互相关联，但是两张表。
Sign 签名研究员给某张已填完的表签字负责该访视/该表填完（或约定节点）之后。建议：硬锁之前关键表都签完。
Freeze 冻结现场先停手，DM 还在收尾可选。末例做完、质疑还剩尾巴时。不是必须节点；KIS 一期可以不做。
Lock 锁库钉死「出报告用的官方版」必须：末例完成 + 开放质疑=0（或 QA 豁免）+ 该关偏差已关 + 该签的已签 + 完整度达标。必须在统计出正式报告之前。
Archive 归档把锁住的那一版打成不可改的证据包必须在硬锁成功且导出批次生成之后（通常统计验收后再归档，以免归档完又要改导出）。

时间轴：开 → 收数 → 关（每一个节点钉死）

  1. T0 建项目（开）配访视、表单、校验规则、谁能填谁能签。此时没有 Query、没有锁、没有归档。技术：方案/CRF 配置表，规则 JSON/表驱动。
  2. T1 入组、每次访视填数（执行）现场保存。校验当场跑。存进去的值才可能被质疑。签出、工单关闭不影响能不能质疑、能不能锁。
  3. T1 同时：Query 窗口打开校验失败可自动开质疑；监查/DM 可手动开。CRC 只能答。DM 决定关不关。只要项目未硬锁，就可以一直开、一直答。
  4. T1 同时：偏差窗口打开超窗、用错仪器走偏差单。QA 关偏差。不关（无豁免）后面不能硬锁。
  5. T2 某张表填完 → 研究员 Sign签名绑的是「这一张表这一版内容」。签完现场改这张表，应作废签名或要求重签（技术上：签名记录带内容哈希）。
  6. T3 末例最后一次访视做完项目进入「收数结束、清洁未结束」。还不能锁，因为质疑可能还开着。
  7. T4（可选）Freeze现场写权限关掉；DM 仍可处理质疑、做受控改数。KIS 可跳过，直接准备硬锁。
  8. T5 硬锁 Lock（关数据，不是关诊所）门禁全绿才能点。点完：该 protocol 所有业务写接口 409。统计还没拿到包，只是库不能改了。
  9. T6 导出批次按 Lock ID 打数据包 + SHA-256。统计只许用这个包。未锁禁止导出「正式分析集」。
  10. T7 统计出报告发现必须改数 → 不能改包内文件。走解锁/锁后改数 → 再锁 → 新批次（旧批次作废但保留）。
  11. T8 归档 Archive（关证据）把 T6 的包 + 质疑终态 + 审计 + 知情方案指针写入对象存储，禁止覆盖。项目在 UI 上标「已归档只读」。这才是合规意义上的「关」。
三句死规定（对应你问的「只能在哪里 / 必须什么时候之后」）

Query：数据进库之后、硬锁成功之前。锁后禁止新开；答也禁止。例外只有「QA 批准解锁」。
Lock：末例完成之后，并且开放 Query=0、偏差收口、关键签名完成。必须在正式统计分析之前。没有「边锁边测」。
Archive：硬锁 + 至少一份带哈希的导出批次之后。不要在还在访视时点归档。

纯技术：每个节点推荐怎么实现（面向 KIS / Django）

原则：校验是写路径上的纯函数；质疑、锁、归档、偏差、签名各自一套业务表。不要用 project.status='done' 一个枚举代替。

1）逻辑核查 = 校验

保存接口里跑规则引擎（表驱动：字段、运算符、阈值）。结果只有：拒绝保存 / 允许但告警 / 允许并发出 RuleFailed。告警若要留合规痕迹，就由监听器创建 Query，不要只弹窗。实现：领域服务 EditCheckService.check(payload)，不要散落在每个 View。

2）Query

推荐：独立表 query_thread + query_message，指向：

protocol_id, subject_id, visit_id?, artifact_type, artifact_id, field_path（artifact_type = 量表格子 / 仪器读数 / 日记格 …）。状态：open → answered → closed（可 reopen）。CRC 只能答；监查/DM 能开；只有 DM/QA 能关。按项目统计开放数，给锁库门禁用。

不要：每个业务表加 query_status 当唯一真相；不要和导检工单一张表；不要只做中间件打日志。硬锁后：写守卫连 Query 的新增也拦住。

3）Sign

推荐：electronic_signature 表：谁、何时、签哪张表、当时内容哈希、含义（「我是研究者，我审过」）。改表后哈希对不上则签名失效，要重签。不要只存 signed=true。

4）Freeze（可选）

推荐：项目状态 soft_frozen + 写守卫：CRC/仪器回写拒绝；DM 允许受控改数（仍写审计）。一期可不上，硬锁复用同一套守卫，只是放行名单更窄。

5）Lock

推荐：声明式锁，不是只改一个布尔。

  • 表 lock_record：项目、操作人、审批人、时间、结果、门禁快照 JSON（当时开放质疑数、偏差数、完整度、豁免单号）。
  • 所有写接口（表、仪器、日记、新开 Query）先 assert_writable(protocol_id)：已硬锁且无有效解锁 → 409。
  • LockGate.evaluate(protocol_id) 失败则按钮禁用。
  • 解锁：新写一条 unlock（QA 审批），不要覆盖旧 lock 行；再锁再插新行。

可用数据库触发器兜底，给检查员看的证据以 lock_record 为准。

6）导出批次（锁和归档中间，不要省）

表 data_export_batch：lock_id、文件地址、SHA-256。未锁禁止创建「分析用」批次。统计只下载这一包，禁止对生产库实时 SELECT 当正式分析。

7）Archive

推荐：MinIO 不可覆盖对象 + 索引表 archive_record。放入：导出 zip、质疑终态、审计、manifest（清单+哈希）、保管到期日。真正适合做切面的是审计日志和这套写守卫，不是 Query。

8）偏差

独立 deviation 表。LockGate 读未关闭数量。可以关联 query_id，不要把超窗做成 Query 类型混进质疑报表。

一期最小集合（形状对，功能可以少） 校验引擎 + Query 两张表 + 签名带哈希 + lock_record（含门禁快照）+ 全写路径守卫（含仪器回写）+ 带 SHA 的导出批次。Freeze、完整文件柜、双人解锁可以二期。不要一期只做 status='locked' 却不算开放质疑数。

1三个概念的本体：先把词钉死

中文现场把 lock、freeze、archive、query、discrepancy、edit check 混着说。论文式研究的第一步是建立可翻译的术语表，否则跨系统比较会比错对象。

LOCK
锁库 / 数据锁定
声明某范围进入官方只读。写路径被拒绝，除非走解锁。
FREEZE
冻结
比硬锁弱：常禁现场改，仍允许 DM 清 Query。Rave 等明确区分。
SIGN
电子签名
研究者对 CRF 负责。签名常是锁的前提，但签名 ≠ 锁库。
ARCHIVE
归档
按留存期封存可核验的证据包。可检索、不可悄悄改、可移交。
QUERY
质疑
对某数据点的正式问答线程。关闭前通常不能锁库。
EDIT CHECK
逻辑核查
规则引擎。可自动发 Query，本身不是 Query。

1.1 为什么必须三分，而不是「质量闭环」一个词

锁库回答的是统计学家的问题：我分析的是哪一版数据？归档回答的是检查员的问题：十年后我如何证明当时那一版没被改过，以及过程文件还在？质疑回答的是监查与数据管理员的问题：这个值为什么可疑，谁解释过，解释是否被接受？三者时序上串行（清 Query → 锁 → 导出 → 归档），对象上正交（Query 指向字段，Lock 指向范围，Archive 指向证据包）。用一张「已闭环」布尔值代替，会在核查时无法出示独立证据。

1.2 与相邻概念的边界

易混词它实际是什么与三概念的关系
源数据核查 SDV把 eCRF 与源文件对照常触发 Query；SDV 完成度可作锁库门禁，但 SDV 不是锁
偏差 / CAPA过程未按方案执行可与 Query 交叉引用；锁库常要求偏差关闭；不是字段级对话
工单 / Ticket运营任务技术形态像 Query；合规上无「指向 ItemData + 审计 + 锁门禁」则不算质疑
备份 Backup灾备副本可被覆盖、轮转；归档要求不可变与哈希证明，备份不够
签出 / 完成访视现场运营状态不等于评估数据已归档（我方访视 PRD 已写明）

2业内如何思考这些问题

成熟产品不是「产品经理发明了锁定按钮」，而是把监管对「可信数据」的要求翻译成状态机。下面按思想来源而不是按厂商排列。

2.1 监管要的不是功能清单，而是可重建的因果链

ICH E6（GCP）把数据完整性表述为：数据应可归属（Attributable）、清晰（Legible）、同时（Contemporaneous）、原始（Original）、准确（Accurate），即 ALCOA，后来扩展为 ALCOA+（Complete, Consistent, Enduring, Available）。锁库服务的是 Accurate + Consistent + Enduring：分析开始后数据集不再漂移。归档服务的是 Enduring + Available：检查时可取出当时的记录。Query服务的是 Attributable + Contemporaneous：可疑值的处理过程本身成为记录，而不是事后口头说明。

21 CFR Part 11 与 EU Annex 11 进一步要求：电子记录的变更要有审计追踪；电子签名要绑定到具体记录；系统要能导出供检查的拷贝。这直接推出：锁不是操作系统权限，而是带身份、时间、范围的业务事件；归档包必须包含审计追踪而不只是当前值。

ICH E9 统计原则强调：分析集应预先定义，数据清理应在盲态或受控条件下完成，锁库时刻应被记录。故 EDC 把「开放 Query 数 = 0」做成硬门禁——不是因为产品经理喜欢清零，而是因为未关闭质疑意味着清理尚未完成，锁库声明在统计上不成立。

2.2 数据管理行业的标准作业（CDM 思维）

国际数据管理学会（SCDM）与各家 SOP 把试验数据生命周期画成大致同一条链：

  1. 建库与 UATeCRF、编辑检查、角色上线。此时无正式数据。
  2. 入组与持续录入自动检查发系统 Query；监查发手动 Query。
  3. 清洁（Cleaning）Query 关闭、SDV、医学审核、编码（MedDRA 等）。
  4. 冻结减少现场改动，留 DM 处理尾巴。
  5. 硬锁 / 数据库锁统计编程以该快照为准；此后改数叫 post-lock change，极重。
  6. 传输与归档ODM/SAS 传输；TMF 收官方拷贝；保留期起算。

思想要点：清洁是过程，锁是截点，归档是保管。用软件实现时，截点必须不可抵赖（谁、何时、何范围、门禁快照），保管必须可核验（哈希、清单、权限分离）。

2.3 两种「锁」哲学：操作锁 vs 声明锁

操作锁（implementation lock）

在记录上置 locked=true，应用层拒绝 UPDATE。开源 EDC（OpenClinica / LibreClinica 的 CRF 锁）和 EHR 的「病历封存」偏这一类。优点是实现直观；风险是没有「锁定事件」实体时，无法证明当时门禁状态。

声明锁（declarative lock）

先写 Lock 记录（范围 + 门禁快照 + 电子签名），再投影到行级只读。Rave / Veeva / 现代 CDMS 偏这一类。统计与 QA 审计的是声明，而不是翻应用日志猜何时变成只读。

对自研的含义KIS 若只在业务表加布尔字段，检查员问「锁的时候还有几条 Query」只能现场查库，而库已经变了。必须把门禁结果冻结进 Lock 记录。

2.4 两种「归档」哲学：库内封存 vs 包外移交

药监检查看 eTMF 与临床数据库是不是能对上。实验室认可（ISO 17025）看原始记录、仪器谱图、报告签发件能否按项目调出。医院病案看封存后的病历是否仍可查阅但不能改。三者都叫归档，保管对象不同：

  • 过程文件归档：方案、知情、伦理、监测访视报告 → eTMF。
  • 分析数据归档：锁库导出 + define.xml + 审计 CSV → 数据室 / 申办者档案。
  • 原始数据归档：仪器文件、图像、日记卡扫描件 → 受控文件库，哈希写入清单。

商业 EDC 往往只把「数据库归档」做成只读研究 + 导出；eTMF 是另一套产品（Veeva Vault TMF、太美 eTMF）。自研若只有一套「归档按钮」，会漏掉检查员要的文件类证据。

2.5 Query 在认知上为什么被抬到与锁库同级

编辑检查可以在保存时弹窗，那只是 UX。监管关心的是：可疑值若被保留，必须留下可检索的处理记录。因此 Query 被设计成独立对象：可统计开放数、可按中心/表单出报告、可作锁库门禁输入。把它做成「字段上的 comment」会在百万级 Item 上无法运营；做成与数据脱钩的聊天会无法证明改的是哪一个值。业内收敛到：指向 Item（或等价节点）的有状态线程。

3锁库：各系统如何设计

OpenClinica 3.x / LibreClinica

开源 EDC 的经典实现。LibreClinica 自 OC 3.14 分叉，锁定模型基本同构。

开源CRF 级锁为主

粒度落在 CRF 版本实例（event_crf / 锁标记）以及研究者电子签名。典型路径：录入完成 → 自动/手动 Query 关闭 → 研究者 Sign → Lock。库级「Database Lock」在社区版里更像运维与 SOP（停止建访视、导出 ODM），而不是单独的一等 Lock 聚合；商业 OC4 把研究级锁定与权限收得更完整。

技术含义：锁是记录状态，审计在独立审计表。解锁需要权限，且应留痕迹。对化妆品功效现场：表单锁有用（某次访视的量表），但「整项目锁」仍要自建，否则仪器回写和日记补录会在「已经出报告」之后继续改数。

Sign ≠ Lock event_crf status discrepancy 清零作 SOP 门禁

Medidata Rave（及 Rave EDC）

行业默认参照系。Freeze / Lock 二分法被后续产品广泛模仿。

商业厂商口径

Freeze（冻结）：数据对站点不可编辑，数据管理仍可处理 Query、执行受控更新。Lock（锁定）：几乎所有角色不可改，除非走正式解锁。粒度可到表单、文件夹（访视）、受试者，再汇总到研究级数据库锁。系统 Query 与手动 Query 的开放数量进入锁定前检查清单（lock checklist），常与 SDV、签名完成度一起出报告。

思想：把「还在清洁」和「已经交给统计」分成两个法律状态，避免过早硬锁导致大规模解锁。Post-lock change 在 SOP 里是偏差级事件。

Veeva CDMS / Vault EDC

与 Vault 平台的对象、工作流、eTMF 同生态。

商业厂商口径

锁定作为 Vault 对象生命周期的状态（与文档锁定同一套权限哲学）。研究、国家、中心、受试者、访视、表单可分层冻结。因为 eTMF 在同一平台，锁库导出与 TMF 里的「数据库锁定证明」更容易对账——这是纯开源 EDC 做不到的产品优势，不是数据模型更神秘。

Viedoc / Castor / 太美 eCollect

中型 CDMS：功能形状接近，计费与建库体验不同。

商业

共性：表单锁 + 研究锁；锁前 Query 报告；锁后只读与导出。Viedoc 公开材料强调锁库后可能产生后续访问费用——说明厂商把「锁后仍要给统计师登录」当成独立产品阶段。Castor 偏研究者自助建库，锁定仍在，但检查清单的刚性因客户 SOP 而异。太美与国产 CTMS 套件绑定，锁库常和项目计划里程碑（LPLV、数据库锁定会）写在同一套项目状态里。

REDCap（对照，非我方可自部署）

学术调查工具。锁定弱于药物 EDC，但「记录锁 / 表单锁」仍存在。

授权限制

记录锁定防止继续修改；仪器对接与纵向事件存在，但没有药物试验那种以 Query 清零为法定门禁的完整 CDM 套件。对照价值：证明「锁」可以很轻；一旦进入申报级人体试验，轻锁不够。

3.1 非 EDC 系统里的「锁」——不要误读

系统有没有试验锁库实际提供的类似物借鉴点 / 陷阱
OpenEyes无病历事件提交后的临床工作流；不是分析集锁定眼科 EPR。勿把「保存病历」当成 GCP 锁库
OpenMRS无Encounter 不可随意删；特权修改；无 Query 门禁EHR 完整性 ≠ 试验数据库锁
Medplum / FHIR需自建Resource.meta、历史版本、Subscription；可用 AuditEvent平台能做版本与审计，锁是业务层
Marley / ERPNext Healthcare无提交后的 DocType 权限、取消凭证；财务意义上的期间关账更接近「锁账」「关账」可类比锁库：期间关闭后凭证不可改，改则红字冲销。值得借会计思想，不要借成 ERP 按钮
LIMS（一般）有「签发」样品结果 Approve / Report issue 后只读实验室「签发」≈ 报告级锁，粒度是样品/报告不是受试者 CRF
综合药物 EDC 把锁做成分层状态 + 检查清单；财务/LIMS 把锁做成「期间关闭 / 报告签发」。KIS 功效评价同时有现场运营和类申报数据，应项目硬锁用 EDC 范式，仪器报告用 LIMS 签发范式，两套锁的范围写进 SOP，避免一张总开关。

4归档：各系统如何设计

4.1 EDC 产品里的归档通常只做「研究只读 + 导出」

OpenClinica / LibreClinica：研究结束后导出 CDISC ODM（含 Audit Trail、Query），数据库可保留只读。没有完整 eTMF。Rave / Veeva：研究归档状态、长期托管、按合同收取归档访问费；Vault 可把锁定证明作为受控文档。Castor / Viedoc：强调 GDPR 下的导出与删除权——归档策略必须同时满足「检查要留」和「隐私要删」，这是 EDC 厂商近十年的新约束，药物 GCP 留存期与个人数据最小化在此冲突，SOP 要写清假名化与分离存储。

4.2 eTMF：另一条归档主链

ICH E6 第八章「必需文件」把方案、知情、伦理批件、监查报告、实验室资质等列成试验主文件。Veeva Vault TMF、太美 eTMF、PhlexTMF 等把「归档」做成：文件夹模型 + 文件生命周期（草稿/生效/过时）+ 检查就绪指标（TMF completeness）。数据库锁的导出包应作为 TMF 的一个工件挂到对应里程碑下，否则统计数据与过程文件会分叉。

4.3 EHR / 眼科 / 医院：病案归档

OpenEyes、OpenMRS 的「归档」接近病案：就诊结束后记录仍可查，修改走修正记录而不是覆盖。这满足医疗质量，不满足「分析集哈希」。Medplum 可用 FHIR DocumentReference + Binary 做文件保管，版本在资源历史中。设计启发：不可覆盖的历史是归档的技术下限；清单 + 哈希 + 留存到期才是合规上限。

4.4 会计类比（ERP）为什么有用

关账后不允许改已过账凭证，只能冲销再生。这与 post-lock change 同构：不删除历史，追加反向记录。归档则像把总账期间连同审计日志刻盘。KIS 若锁后仍 UPDATE 原行，既不像 EDC 也不像会计，是最难向检查员解释的实现。

4.5 归档包建议结构（跨系统收敛出的最小充分集）

  1. manifest.json：项目、Lock ID、时间、操作人、文件列表、SHA-256。
  2. clinical data：ODM 或等价表 + 字典。
  3. audit：字段级变更。
  4. queries：全部线程终态，含关闭理由。
  5. lock certificate：门禁快照（开放 Query 数、完整度、偏差数、豁免单号）。
  6. pointers：TMF 路径、原始仪器包路径（可外链，哈希必须在清单内）。

对象存储写一次（WORM / 合规保留模式更佳），生产库保留只读投影以便业务查询。到期销毁走审批，与备份轮转策略分离。

5质疑（Query）：各系统如何设计

5.1 标准生命周期（几乎所有 EDC 同构）

  1. 打开系统规则触发，或 CRA/DM 手动创建。绑定到 Item / 表单 / 访视。
  2. 通知站点工作队列；有的发邮件。Query 是任务，不是日志。
  3. 应答站点解释或改值。改值必须走审计（旧值、新值、原因）。
  4. 关闭或再打开DM 接受则关闭；不接受则更新线程继续。关闭码（确认数据正确 / 已修正 / 无法获得）进入统计。
  5. 与锁耦合开放 Query 阻断硬锁；豁免必须书面且进入 Lock 快照。

5.2 LibreClinica / OpenClinica：Discrepancy Note

实现名不叫 Query 而叫 Discrepancy Note。类型大致包括：Failed Validation（系统）、Query（人工）、Reason for Change、Annotation。状态机：New → Updated → Resolution Proposed → Closed（名称因版本略异）。线程挂在 item_data。这是「质疑 = 数据点上的有状态注解」的教科书实现。系统校验失败可以自动开 DN，与手动 Query 共用存储，用类型字段区分——注意：共用存储不等于同一业务语义，报表要能拆开。

5.3 Rave / Veeva / 太美：运营型 Query 管理

除生命周期外，强调：按中心老化（aging）报表、Query Rate 作为监查指标、系统 Query vs 手动 Query 占比（系统过多说明检查太噪，手动过多说明建库不足）。Veeva 把 Query 当 Vault 对象，可走工作流、权限、与 SDV 状态并列。太美把质疑和国内监查习惯（中心沟通、纸质溯源）做在同一操作台。产品差异在运营，不在「要不要独立对象」。

5.4 Castor / REDCap：更轻

Castor 有 Query 模块但研究者自助研究里使用深度不如申办者级 CDM。REDCap 有 Data Resolution Workflow（可开关），很多队列研究关掉它，只用调查逻辑。对照说明：Query 的完整形态是监管强度的函数，不是所有采集系统的必选模块；一旦宣称符合 GCP 数据采集，它就变成必选。

5.5 EHR 里有没有 Query？

OpenMRS / OpenEyes 没有试验 Query。接近物是：临床消息、结果异常旗标、修正说明。FHIR 有 Flag、DetectedIssue、Communication——可以映射「有个问题」，但没有与 Database Lock 的标准耦合。若在 EHR 上做试验，仍应引入独立 Query 聚合，而不是复用聊天。

5.6 Query 与编辑检查、偏差、工单的四象限

自动规则人工发起
针对数据值系统 Query / Failed ValidationCRA 质疑某血压
针对过程超窗自动开偏差（有的系统）偏差 / CAPA、现场工单

同一现象可以升格：重复超窗的 Query 批量升级为偏差。模型上应允许链接，而不是互斥。KIS 现场工单（导检、称重）落在「过程 × 人工」象限，不要塞进 Query 表；仪器读数异常落在「数据 × 自动」象限，应开 Query 或等效数据质疑。

7技术命题：Query 是不是一道抽象切面？

这是本报告要单独写透的问题。结论先给：挂载方式应当切面化；Query 自身必须是领域一等公民。只做切面、不做聚合根，不够；只做工单、不会挂到任意数据节点，也不够。

7.1 「切面」在软件里通常指什么

AOP 意义上的切面：在不修改业务函数的前提下，对「调用」织入日志、权限、事务。如果把 Query 做成：任何 save_field 之后跑规则、发一条通知——这只覆盖了系统 Query 的产生，没有覆盖人工 Query、线程、关闭码、锁门禁、导出。所以「Query = 保存拦截器」是一个过小的切面。

另一种「切面」是 DDD 里的横切关注点：审计、多租户、软删除。Query 比这些更重：它有自己的生命周期、参与者、SLA、报表，会反向约束其他聚合（未关闭则不能 Lock）。横切关注点一般不反向把门禁加到核心流程上；Query 会。因此把它仅仅登记为基础设施切面，会在分层上放错位置。

7.2 业内实际采用的结构（可称作「附着切面 + 聚合根」）

所有严肃 EDC 都满足两点：

  1. 多态指向：Query.target = (entity_type, entity_id, optional json_path / item_oid)。这是切面性：表单模块、仪器模块、日记模块不必各写一套质疑表。
  2. 独立聚合：Query 有 id、状态机、评论集合、关闭原因、创建者角色。锁库服务只问 QueryRepository.count_open(protocol_id)，不解析各业务表。

这正是「内容管理系统里的评论」或「文档系统里的批注」：批注系统是平台切面，但每条批注是一等对象。GitHub Review Comment、Google Docs Suggestion 都是这个结构。Query 比普通评论多了：与值版本绑定（评论时的 old_value）、与审计改数事务的可选关联、对 Lock 的否决权。

7.3 若做成纯切面，会在哪里失败

  • 无法列出「本中心开放 Query」工作队列（切面没有列表模型）。
  • 锁库门禁只能扫描业务表猜「有没有问题」，无法可重复计算。
  • 归档包缺少 Query 终态，检查员看不到清洁过程。
  • 人工质疑没有第一类入口（CRA 不是在 save 时被拦截，而是主动创建）。

7.4 若做成纯工单（无指向切面），会在哪里失败

  • 仪器、图像、日记、CRF 各做工单类型，统计开放数无法统一。
  • 改的是「工单」不是「那个血压值」，审计对不上 Item。
  • 同一字段两条质疑无法与字段 UI 角标集成。

7.5 推荐的技术形态（给实现者的规格级描述）

推荐

Query 有界上下文，对内聚合根 QueryThread：状态、类型（system/manual）、关闭码、消息列表。指向为值对象 DataRef{protocol_id, subject_id, visit_id?, artifact_type, artifact_id, field_path}。产生通过领域事件：FieldSaved、RuleFailed、ManualQueryRequested。消费：工作台列表、CRF 控件角标、LockGate.count_open。权限按角色（站点只能答，DM 能关）。不要在每个 Django Model 上复制 query_status 列作为唯一真相——那是投影，真相在 Query 表。

规则引擎是另一切面：它只负责决定要不要开 Query，开出来的还是 Query 聚合。偏差是第三聚合，可用 related_query_ids 链接。现场运营工单是第四聚合，artifact_type 不含 eCRF 字段则不要进 Query 门禁，以免导检单挡住锁库。

7.6 与审计追踪的关系

审计是真正适合做纯切面的东西：所有写操作织入 append-only 日志。Query 消息写入也应进审计，但 Query 状态机不是审计的派生物——不能从日志「还原出」运营队列（能，但贵且不可作为在线模型）。业内因此分表：audit_event 与 discrepancy_note 并存。

8对 KIS（化妆品人体功效 / 类 GCP）的含义

选型报告已指出通用 EDC 只覆盖需求的一小部分，现场运营必须自研。机制上仍应照抄 EDC 的三件套形状，不要照抄其 CRF 中心论：

  1. 锁：按 protocol_id 做声明式硬锁 + 门禁快照；访视/表单软锁可后补。仪器签发与项目硬锁分范围。
  2. 归档：锁库导出批次（哈希）是数据归档；知情/偏差/培训进质量档案（TMF 子集）；签出不是归档。
  3. Query：独立聚合 + DataRef 切面挂到量表字段、仪器读数、日记缺失。不要与导检工单一张表。开放 Query 进锁库门禁；工单另算。
第一期可以砍范围，不能砍形状不做 Freeze 分层可以；做硬锁却不保存门禁快照不行。不做 eTMF 全文件夹可以；导出无哈希不行。Query 可以先只支持手动 + 一种系统规则；但不能没有线程和指向。

8bGreat Expectations / Soda / Deequ / OHDSI DQD：对思考 Query、Sign、Lock、Archive 有没有帮助

这四套都是「数据质量（Data Quality）」工具，主要跑在仓库、Spark 表、观测型医疗数据模型上。它们和临床试验里的质疑、签名、锁库、归档同属「让数据可信」这条大河，但不是同一段河道。结论可以先记：对逻辑核查（校验）和锁库前门禁里的「完整度/一致性扫描」很有帮助；对 Sign、Lock 声明、Archive 证据包、以及作为正式问答的 Query，不能替代，最多当发动机。

一句话对照 EDC 的 Query 是「贴在某一个受试者某一个格子上的、有人答、有人关的工单」。这四套工具产出的是「这张表 3% 空值、这一列有 12 个超范围」——更像批量体检报告。体检报告可以自动拆成很多张 Query，但它自己不是 Query 生命周期，更不会给人的电子签名或锁库法律声明。

它们到底在干什么（用人话）

Great Expectations（GX）

Python。「我期望这张表满足一组 Expectation。」跑完得到成功/失败清单和文档化的 Data Docs。

典型检查：这一列非空、唯一、取值在枚举里、均值在区间、表行数大于昨天。可以挂在 CI 或每晚批处理。它解决的是数据集是否符合契约，不是「37 号受试者这一格谁解释过」。

Soda Core

YAML/SodaCL 写检查，对仓库跑 scan。和 GX 同类，偏「数据契约 + 观测」。

对思考有帮助的部分：把「什么叫合格」写成可版本管理的检查文件，失败进告警。对 Sign/Lock/Archive 没有现成对象。许可见上表，不要只看「GitHub 上有代码」就当 Apache。

Deequ（AWS Labs）

在 Spark 上算约束：唯一性、完整性、模式、近似分位数。可推「数据质量指标」随时间变没变。

适合：仪器明细、日记大表进数仓之后做锁库前扫描——「关键字段完整度是不是 100%」。不适合：访视当时的弹窗校验（太重），也不签发锁。

OHDSI DataQualityDashboard

给 OMOP 标准化后的观察性数据做 DQ：概念对不对、日期逻辑、性别与妊娠冲突等。结果是仪表盘 + 检查条目级通过/失败。

对思考最有启发的不是「化妆品要用 OMOP」，而是：质量检查是一份可引用的目录（check_id）+ 一次运行的结果快照。这很像锁库门禁快照该有的形状。但它假设数据已经在 CDM 里，没有研究者签名、没有试验锁、没有 TMF。

映射到 Query / Sign / Lock / Archive（这是关键）

概念 这四套直接提供吗 有帮助的用法 若误当成替代品会怎样
逻辑核查 Edit check 几乎就是这类工具的本职（批量版） 把「规则」从代码里抽成可测的 Expectation / Deequ constraint / DQD check。保存时用轻量规则；锁库前用 GX/Deequ 扫全表。 无。这是正配。
Query 质疑 不提供「人与人的线程」 批处理失败行 → 生成系统 Query（带 DataRef）。GX 的 validation result 当「开单原因」快照存进 query_thread。 只有失败报表、没有 CRC 应答、DM 关闭，锁库门禁无法问「开放质疑数」。
Sign 签名 无 几乎无。DQ 跑得过不等于研究者对 CRF 负责。不要用「质量扫描通过」代替电子签名。 检查员问谁对医学内容负责，你出示一份 GX HTML，对不上 Part 11。
Freeze / Lock 无锁记录、无写拒绝 把扫描结果写进 lock_record 的门禁快照：complete%、失败 check 列表。扫描通过是锁的条件之一，扫描动作不是锁。 「DQ 全绿」后现场还能改数，统计仍会漂。
Archive 归档 只有「运行产物」可当附件 把某次 GX/Deequ/DQD 的 run_id、结果 JSON、Data Docs 打进归档包，证明「锁的时候质量扫描长这样」。这是证据，不是归档本身。 只保存最新一次扫描，覆盖历史，等于没有当时快照。

对「怎么思考」具体有哪些帮助

  1. 把校验想成可版本管理的契约，而不是 if 语句。GX Expectation、Soda check、Deequ constraint 都强迫你写出「这一列必须怎样」。临床试验的 edit check 清单、锁库完整度定义，应用同一纪律：规则有编号、有版本、改规则要记录。
  2. 区分「行级实时」和「表级批处理」。保存时的校验必须毫秒级（自研轻量引擎）。四套工具擅长扫十万行仪器明细。锁库前门禁适合跑后者：空值率、重复受试者、访视日期倒置。不要用 Spark 卡保存按钮。
  3. 失败要落成对象，不要只报警。数据工程习惯 Slack 告警；GCP 习惯 Query。正确接法：DQ 失败 → 事件 → 按失败行展开成 QueryThread（能展开到 subject+field 的才开 Query；只能说「整列 3% 空」的，记成偏差或锁库阻断项，不要假装是字段质疑）。
  4. OHDSI 教你「检查目录 + 一次运行」。DQD 每条检查有稳定 ID。你们的 LockGate 快照应引用 check_id + run_id + pass/fail，而不是锁的时候口头说「我们看过了」。
  5. Deequ 的「约束 vs 指标」。约束失败应阻断锁；指标（均值漂移）更适合告警或开「医学审核」类 Query，不一定自动硬阻断。这能避免把统计波动当成数据错误。

对「怎么思考」没有帮助、甚至有害的地方

  • 没有角色。没有 CRC/DM/研究者。质量平台默认是数据工程师看仪表盘。试验 Query 必须按角色答和关。
  • 没有法律截点。DQ 每天跑、结果会变。Lock 必须是「这一刻」的声明。所以锁的时候要冻结那一次 run 的结果进 lock_record，而不是锁后再跑一遍 DQ 覆盖。
  • 没有签名含义。Expectation 通过 ≠ 「我是研究者」。
  • 粒度常常是列/表，不是受试者×访视×字段。不拆行就无法开合规 Query。
  • OHDSI 的世界是 OMOP，不是 eCRF。借鉴检查思想；不要为了用 DQD 先把功效评价硬转成 OMOP（除非你们另有真实世界数据战略）。

若接到 KIS：推荐的技术接法（仍保持三概念形状）

  1. 在线路径保存 → 自研 EditCheckService → 可选自动开 Query。这里不用 GX/Deequ。
  2. 锁库前批路径把分析用宽表或导出候选表丢进 GX 或 Deequ → 得到 run 结果。LockGate 读取：阻断类失败则 passed=false；并把 run 摘要写入 lock_record.gate_snapshot。
  3. 失败行展开能映射到 DataRef 的，upsert 系统 Query；不能映射的，记 lock blocker 或偏差，禁止冒充 Query。
  4. 归档该次 DQ run 的 JSON/HTML 作为 archive 附件，manifest 记哈希。签、锁表仍是你们自己的表。
选型建议 思考与一期锁库扫描：优先 Great Expectations 或 Deequ（Apache-2.0）。OHDSI DQD 当「如何给检查编号、如何展示失败」的教材，不要当试验 EDC。Soda Core 先用法务看 ELv2，再决定能否进发行产品。四套加在一起也填不满 Query 线程、Sign、Lock 声明、Archive 包——那些仍按第 0c 节自研。
